# Fund 币种与金额单位排查

> 历史诊断与设计讨论，2026-09-25 复核归档。下文“当前”均指 9 月 17 日排查时点，不代表现行实现。后续 [PR #25](https://github.com/zephyrli-coding/vestoria-fund-manager/pull/25) 已合入 main，实现 Data Terminal 汇率接入、统一展示币种与币种修改保护；详见 [9 月 19 日实现记录](2026-09-19-data-terminal-fx.md)。数值精度以[后续精度记录](2026-09-19-display-precision.md)为准。

日期：2026-09-17。范围：当时 `main` / 生产部署 `d8c9b2a` 的代码、生产 SQLite 只读一致性检查。该轮仅排查，没有修改业务代码、生产数据或部署。公开归档省略具体业务规模与核账差值。

## 结论

生产数据没有发现非法币种或大范围账务计算损坏；主要问题是币种数据模型过薄，加上总览页面同时使用三套不同统计口径，使 CNY / USD 开关看起来像统一单位切换，实际并不是。

### 1. 同一总览页的币种口径不一致

`Dashboard.tsx` 中：

- “人民币资产 / 美元资产”卡片分别只加总原币种基金，不换汇。
- 资产趋势把所有基金用固定 `1 USD = 6.9 CNY` 合成一条总资产曲线，再按开关显示 CNY 或 USD 等值。
- 资产分布和基金列表只显示当前所选原币种基金。

因此选择 CNY 时，卡片、趋势、分布分别表示“CNY 原币资产”“全部资产的 CNY 估值”“仅 CNY 基金”；USD 同理。界面没有把这三个集合差异放在主要标签上，用户会自然理解成同一批资产切换显示单位，造成金额互相对不上。

统一 UI 之前的首页“总资产”同时给出全部资产的 CNY / USD 等值；2026-09-05 改版后卡片变为两个原币种小计，但历史趋势仍保留全部资产换汇估值，形成当前不一致。

### 2. 汇率是前后端各自写死的常数

前端 `frontend/src/utils/fundFormatting.ts` 和后端 `backend/app/repositories/fund_repo.py` 都独立写死 6.9。它不是实时或按日汇率，也没有来源、日期、配置或版本字段。

后端聚合历史时，将 USD 基金的每条历史余额统一乘 6.9，并将最终 CNY 总额除以 6.9 得到 USD 曲线。这不是历史时点估值；以后修改常数会让整条历史曲线一起变化。

基金列表的“按资产估算”排序也使用前端常数，所以前后端常数漂移时，排序和趋势会采用不同口径。

### 3. 币种只是 Fund 当前元数据，历史记录没有币种

`funds.currency` 是唯一币种字段；`fund_history`、`operations`、`investors`、投资者收益快照均不保存币种或金额单位。

编辑基金时前端仅提示“不会自动换汇或重算历史金额”，后端仍允许直接修改币种。修改后：

- 当前余额、累计投入/赎回、操作金额和历史余额的数值不变；
- 所有页面会立刻改用新币种符号；
- 聚合历史会按新币种对全部旧记录重新决定是否乘 6.9。

这会把一次元数据编辑变成对全部历史金额语义的追溯性改写，而且数据库无法判断某条旧记录原来是什么币种。

### 4. “单位”只有符号，没有可审计的显示单位

金额格式化只在数字前加 `¥` 或 `$`，固定显示两位小数。数据模型没有“元 / 万元”“美元 / 万美元”等 scale 字段；图表 Y 轴对任何币种超过 10,000 都显示中文“万”，且轴本身不显示币种符号。页面也没有统一说明数据库数值必须以一个完整货币单位录入。

这不会自动把数值乘错，但无法防止用户按“万”为单位录入，且同一张图的轴标签很容易被误读。

## 生产只读检查

- 生产仓库：`main`，SHA `d8c9b2a`，工作区干净。
- SQLite `PRAGMA integrity_check`：`ok`。
- 已检查基金的币种均为 CNY 或 USD，没有其他币种代码。
- 基金余额、总份额 × NAV 与投资者余额合计基本一致；当时观察到的少量差值处于 Float / 六位份额与显示取整边界内，不构成这次单位问题的主要原因。
- 生产库已有基金历史和操作记录，但相关表没有币种快照，因此无法仅凭数据库还原是否发生过币种元数据更改。

## 当前判断

优先级最高的根因是总览口径混用，其次是可修改币种但历史不存币种。固定 6.9 和图表“万”属于会持续制造误解的设计债务。

产品口径现已确定：总览的 CNY / USD 开关表示“全部资产的展示币种”。基金、历史记录和流水继续保留原币金额；切换只改变查询结果和界面的换算展示，不修改账本数据。

## USD/CNY 汇率渠道调研

以下为 9 月 17 日的渠道核查与方案建议，不是 9 月 25 日重新联网实测。最终实现通过 Data Terminal 个人 API key 读取 ECB 汇率；本文提及的备用源与交叉校验属于当时建议，不能视为已经实现。

Fund 是估值看板而不是交易撮合或结算系统，因此采用每日参考汇率即可。综合官方性、可编程访问、生产网络可达性和接入成本，建议以 **ECB 每日参考汇率 API 为主源**。

| 渠道 | 数据性质 | 接入情况 | 适合度 |
| --- | --- | --- | --- |
| ECB Data Portal | 官方每日参考汇率；工作日发布 | 免费 SDMX 2.1 API，无需密钥；本地和 `sg01-daily` 实测 HTTP 200 | **首选主源** |
| CFETS / 中国货币网 | 中国外汇交易中心发布的人民币中间价 | 官方性最强，但稳定的程序化数据服务主要通过 CMDS、授权数据商或商业许可提供；公开网页不适合抓取 | 获得授权后可作为中国口径主源 |
| FRED `DEXCHUS` | 美联储 H.10，纽约市场人民币兑美元每日午间买入价 | API 需要密钥；本地和 `sg01-daily` 测试时 CSV 端点超时 | 交叉校验，不作为当前主源 |
| Frankfurter | 开源汇率 API，可指定 ECB provider | 无密钥、可自托管；本地和生产实测可达 | 可作为 ECB 的技术代理或备用，不宜成为无来源标记的独立口径 |
| ExchangeRate-API / Twelve Data | 商业汇率 API，付费档提供更高频率和 SLA | 接入简单，但增加订阅、密钥和授权约束 | 需要盘中实时价或商业 SLA 时再选 |

### 推荐实现

ECB 的 USD 和 CNY 序列都以 EUR 为基准，应按同一估值日计算：

```text
USD/CNY（1 USD 可兑换多少 CNY） = CNY/EUR ÷ USD/EUR
```

接口可一次请求两条日频序列：

```text
https://data-api.ecb.europa.eu/service/data/EXR/D.USD+CNY.EUR.SP00.A?format=csvdata
```

2026-09-17 实测接口最近五个工作日的衍生 USD/CNY 分别为 6.706267、6.708247、6.708424、6.711500、6.707116，最近数据日期是 2026-09-16。Frankfurter 的最近 ECB 值为 6.7071，二者一致。

服务端应每天抓取一次，把 `rate_date`、`usd_cny`、两条原始 EUR 交叉汇率、`source` 和 `fetched_at` 持久化。当前总览使用最近一个有效工作日的汇率；历史曲线按各历史日期对应的汇率估值，周末和节假日沿用前一个有效工作日。金额和汇率使用 Decimal，原币账本不做覆盖或重算。

主源失败时继续使用数据库中最近一次成功值，并在界面明确显示来源、汇率日期和“数据已过期”；不得悄悄退回固定 6.9，也不得在不记录来源的情况下切换供应商。Frankfurter 可作为请求 ECB 数据的备用技术路径，但仍记录 `source=ECB`。FRED 可定时做独立交叉检查；若偏差超过约 0.5%，告警并保留原值等待核查。

页面建议显示：`估算汇率 1 USD = 6.7071 CNY · ECB · 2026-09-16`。ECB 明确说明参考汇率仅供信息使用，不适合交易结算；这与 Fund 的展示估值用途匹配。

### 系统归属

汇率采集、历史留存和来源审计应统一放在 Data Terminal，Fund 后端通过内部 API 批量读取当前及历史汇率，并保存最近成功缓存。Data Terminal 当前 Yahoo Fetcher 已能取得 `CNY=X`，但还没有正式 forex 类型、专用 Decimal 汇率表或汇率 API，因此不能直接把普通行情接口当成最终契约。主源仍采用 ECB；Yahoo 只做独立校验，Fund 不直接请求外部数据源。
